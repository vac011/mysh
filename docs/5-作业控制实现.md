# 5. 作业控制实现

## 本节背景

前四个阶段已经建立了从输入文本到进程执行的完整链路，但 executor 仍然把每次执行看成一组必须立即等待结束的子进程。它无法将任务放到后台异步执行，也不能在前台任务执行过程中使用 `Ctrl-Z` 暂停它。

作业控制需要同时处理三个层次：

- **PID（Process ID）**：标识一个具体进程, 每个进程都有自己的 PID, `fork()` 创建的子进程会获得新的 PID, `exec()` 只替换当前进程的程序映像, 不会改变 PID。
- **PGID（Process Group ID）**：标识一个进程组。每个进程都恰好属于一个进程组，同一进程组中的多个进程可以被统一等待和发送信号。**进程组组长**的 **PID 与 PGID 相等**，但组长结束退出后，其他成员仍然可以继续留在这个 PGID 中，直到最后一个成员退出或离开进程组。shell 通常把同一条管道中的全部进程放入同一个进程组，并把这个进程组作为一个 Job 管理。
- **SID（Session ID）**：标识一个会话。一个会话包含一个或多个**完整的**进程组(即进程组不可跨会话)。**会话首进程**的 **PID 与 SID 相等**；即使会话首进程之后退出，其他成员仍然可以继续保留原 SID。控制终端与会话关联，并在该会话的多个进程组中选择一个作为**前台进程组**。终端并不会把 `Ctrl-C`、`Ctrl-Z` 等输入发送给“shell 当前正在等待的 PID”，而是发送给终端当前的**前台进程组**。

三者形成的关系是“一个会话包含多个进程组，一个进程组包含多个进程”：

```text
Session（SID = S）
├── shell 进程组（PGID = P0）
│   └── mysh（PID = P0）
├── Job 1 / 进程组（PGID = P1）
│   ├── command1（PID = P1，进程组组长）
│   ├── command2（PID = P2）
│   └── command3（PID = P3）
└── Job 2 / 进程组（PGID = P4）
    └── command4（PID = P4）
```

这里的 Job、Process 是 shell 在用户空间维护的数据结构，而 `PID`、`PGID`、`SID` 是内核维护的进程属性。mysh 通常让一个 Job 对应一个 PGID，让一个 Process 节点对应一个 PID；shell 显示的 job ID 则只是作业表中的编号，与 PID、PGID 和 SID 都不是同一个概念。

`fork()`、`setpgid()` 和 `setsid()` 对这三个层次的影响也不同：

- `fork(void)` 创建一个拥有新 `PID` 的子进程，子进程会**继承**父进程的 `PGID` 和 `SID`。因此 executor 刚 fork 出来的子进程最初仍属于 shell 的进程组，必须在开始执行用户命令前调用 `setpgid()`，把它移动到对应 Job 的进程组。

- `setpgid(pid, pgid)` 在**当前会话内**创建或调整指定进程所在的进程组。
  - 如果 `pid` 等于 0, 则表示对当前进程设置。
  - `pgid` 只能为两种值: 要么**等于目标进程 PID 或 0**, 则创建一个新进程组并使该进程成为新进程组的组长; 要么**等于一个已有的进程组ID**, 并将目标进程加入该组。
  - 一个进程的 PGID 只能由自己设置, 或在**未进行 `exec()` 操作前**由**直属父进程**设置。
  - 不能将进程移动到其他会话中的进程组;
  - 不能修改**会话首进程**的进程组, 也不能修改**进程组组长**的进程组。

- `setsid(void)`: 不接收任何参数, 会**根据进程自身的 PID 同时创建一个新会话和一个新进程组**，使调用进程成为会话首进程及进程组组长，此时 `SID == PGID == PID`，并且新会话最初没有控制终端。
  - 一个会话至多拥有一个控制终端，而一个终端至多被一个会话控制, 但二者一旦绑定一般无法更改。控制终端在任意时刻只记录一个**前台进程组 PGID**。同一会话中的其他进程组都是后台进程组：后台进程仍然可以运行，但读取控制终端时通常会收到 `SIGTTIN`; 尝试写入控制终端或调用`tcsetgrp`尝试成为前台进程组时通常会收到 `SIGTTOU`。
  - 由于一个已有进程组的组长无法调用 `setsid()` 成为新会话首进程，会以 `EPERM` 失败，因此守护进程通常先 `fork()`、再由子进程调用 `setsid()`, 然后通过 `ioctl(fd, TIOCSCTTY, ...)` 把一个 terminal 设备设置成当前 session 的 controlling terminal。
  - mysh 不需要调用 `setsid()`。它由终端中的外层 shell 或终端环境启动，应该继承现有会话和控制终端, 如果重新创建会话，反而会脱离当前控制终端环境。mysh 只需保证自己的 PGID 与 Job 的 PGID 不同，然后通过 `tcsetpgrp()` 在这些进程组之间切换**终端前台所有权**。
  
## 本节目标

- 识别命令末尾的 `&`，使命令能够在后台启动并立即返回 REPL；
- 使用进程组把同一条管道中的所有进程组织成一个 Job, 并将所有 Job 维护成一条作业链表;
- 初始化交互式 shell 的进程组、终端所有权和信号策略；
- 阻塞等待前台 Job，非阻塞回收后台 Job，并处理停止和继续事件；
- 实现 `jobs`、`fg` 和 `bg` 内置命令。

## 实现

### 5.1 解析后台执行符号 `&`

`&` 与管道符、重定向符一样，只在普通引号状态下具有语法含义；位于引号中或被反斜杠转义时，它仍然属于 WORD。**整条管道**将会作为一个整体放入后台，当前实现中 `&` 必须是输入中的最后一个非空白字符，而不是像完整 Bash 那样可以作为分隔符分隔后续命令(同时将前面一串命令放入后台)。

- `tokenizer` 增加 `TOKEN_AMP`。扫描到普通状态下的 `&` 后，继续检查剩余字符是否全为空白；如果后面仍有内容，就直接报告语法错误。
- `parser` 只负责把这一 Token 转换为命令串的后台执行标识 `Commands.background`。
- `executor` 随后根据该标志决定执行及等待策略。

无命令重定向位于后台管道末尾时，Bash 与 zsh 还存在一个语法边界差异：

```sh
printf aaa | > output &
```

GNU Bash 接受这种写法：最后一段被解析为只有重定向的空命令，`&` 再把整条管道放入后台。而 macOS zsh 原生模式则会在 `&` 附近报告语法错误。这属于不同 shell 对 null command 与后台控制符组合方式的语法选择，不是 macOS 或 Linux 内核造成的差异。

mysh 这里选择与 Bash 一致：tokenizer 只要求 `&` 是最后一个非空白字符；parser 又允许当前 Command 没有 `argv` 但拥有重定向，因此上述后台写法可以正常得到 `Commands.background = 1`。无命令 Command 的具体执行方式已经在 3.7 节通过 `builtin_null` 处理。

```c
// tokenizer.h
typedef enum {
    TOKEN_WORD,
    TOKEN_PIPE,
    TOKEN_REDIRECT_IN,
    TOKEN_REDIRECT_OUT,
    TOKEN_REDIRECT_APPEND,
    TOKEN_AMP,
    TOKEN_EOF
} TokenType;
```

```c
// tokenizer.c
case '&': {
    end++;
    while (*end != '\0') {
        if (!isspace((unsigned char)*end)) {
            fprintf(stderr,
                    "syntax error: '&' not in the end\n");
            goto failed;
        }
        end++;
    }
    token_type = TOKEN_AMP;
    token_value = strdup("&");
    if (token_value == NULL) goto failed;
    break;
}
```

```c
// parser.h
typedef struct Commands {
    Command *command;
    int pipeline;
    int background;
} Commands;
```

```c
// parser.c
if (type == TOKEN_AMP) {
    commands->background = 1;
}
```

executor 加了 builtin 的分派条件。只有**独立**、**前台**的 **builtin** 可以直接在父 shell 中运行；一旦带有 `&`，父 shell 就不能停在 builtin 中完成执行，否则命令并没有真正异步。

```c
char* fn_name = (commands->command->argv == NULL) ? NULL : commands->command->argv[0];
builtin_fn fn = lookup_builtin(fn_name);
// 只有独立前台 builtin 才会在父 shell 中直接运行。
if (fn && !commands->pipeline && !commands->background) {
    // 在父 shell 中直接执行独立前台 builtin。
} else {
    // 否则都去 fork。因为管道要求并行, 而后台要求异步, 这两种情况下都不能直接在父 shell 中执行。
}
```

### 5.2 Job 实现

#### 5.2.1 定义 Job 与 Process 结构体

Job 保存同一串命令对应的 Job ID、进程组 ID、 Process 链、管道最后一个进程的 PID(作为该串管道命令的返回值)、命令原字符串(用以查看 Job 时显示)、终端属性(用于在终端控制权切换时保存和恢复自身的终端状态)、Job状态和后台执行标识等。

Process 保存着进程的 PID、运行状态以及被父进程回收时的状态等。

```c
// job.h
typedef enum {
    RUNNING,
    STOPPED,
    DONE
} Status;

typedef struct Process {
    pid_t pid;
    Status status;
    int wait_status;
    struct Process *next;
} Process;

typedef struct Job {
    size_t job_id;
    pid_t pgid;
    char *cmd;
    Status status;
    int background;

    Process *processes;
    pid_t last_pid;

    struct termios terminal_models;
    struct Job *next;
} Job;
```

#### 5.2.2 Job 创建与添加 Process

创建 Job 时只初始化与命令本身有关的字段。第一个子进程 fork 成功后，才把它的 PID 同时作为 Job 的 PGID；每加入一个 Process，就更新 `last_pid`，使其最终指向管道最后一条命令对应的进程。

```c
Job *create_job(int background, const char *command_string) {
    Job *job = malloc(sizeof(*job));
    if (job == NULL) return NULL;
    // cmd 要深拷贝, 因为输入命令字符串在下一轮 REPL 前就会被释放, 而 Job 可能在后台持续很久。
    job->cmd = strdup(command_string);
    if (job->cmd == NULL) {
        free(job);
        return NULL;
    }

    job->job_id = 0;
    job->pgid = 0;
    job->status = RUNNING;
    job->background = background;
    job->processes = NULL;
    job->next = NULL;
    job->terminal_models = shell.terminal_modes;
    return job;
}

int add_process(Job* job, pid_t pid) {
    Process* process = malloc(sizeof(Process));
    if (process == NULL) return -1;
    process->pid = pid;
    process->status = RUNNING;
    process->wait_status = 0;
    process->next = NULL;
    if (job->processes == NULL) {
        job->processes = process;
        job->pgid = pid;
    } else {
        Process* p = job->processes;
        while(p->next != NULL) p = p->next;
        p->next = process;
    }
    job->last_pid = pid;
    return 0;
}
```

#### 5.2.3 更新 Job 与 Process 状态

Job 的状态必须由所有 Process 共同决定：

- 只要还有一个进程处于 RUNNING，整个 Job 就仍是 RUNNING；
- 如果已经没有运行进程，但至少存在一个 STOPPED 进程，Job 为 STOPPED；
- 只有全部 Process 都为 DONE 时，Job 才真正结束。

```c
static Status calculate_job_status(const Job *job) {
    int has_stopped = 0;

    for (const Process *process = job->processes;
         process != NULL;
         process = process->next) {
        if (process->status == RUNNING)
            return RUNNING;
        if (process->status == STOPPED)
            has_stopped = 1;
    }

    return has_stopped ? STOPPED : DONE;
}
```

每次 `waitpid()` 返回后，先根据 W 系列宏更新对应 Process，再重新计算 Job 状态。

```c
static void update_process(Job *given_job,
                           pid_t pid,
                           int status) {
    Job *job =
        given_job == NULL ? shell.jobs : given_job;

    while (job != NULL) {
        for (Process *process = job->processes;
             process != NULL;
             process = process->next) {
            if (process->pid != pid)
                continue;

            Status old_status = job->status;

            if (WIFEXITED(status) || WIFSIGNALED(status))
                process->status = DONE;
            else if (WIFSTOPPED(status))
                process->status = STOPPED;
            else if (WIFCONTINUED(status))
                process->status = RUNNING;

            process->wait_status = status;
            job->status = calculate_job_status(job);

            if (given_job == NULL &&
                job->status == DONE) {
                job_remove(job);
            } else if (given_job == NULL &&
                       job->status == STOPPED &&
                       old_status != STOPPED) {
                job_make_current(job);
                printf("[%zu]+ Stopped %s\n",
                       job->job_id, job->cmd);
            } else if (given_job == NULL &&
                       job->status == RUNNING &&
                       old_status == STOPPED) {
                printf("[%zu]+ Continued %s\n",
                       job->job_id, job->cmd);
            }
            return;
        }

        job = given_job == NULL ? job->next : NULL;
    }
}
```

### 5.3 终端控制初始化

作业控制只对连接到控制终端的交互式 shell 有意义。`-c` 和脚本模式不需要争夺终端，也不能使用 `fg`、`bg` 操作交互式作业，因此 controller 首先记录 `interactive`，非交互模式完成普通字段初始化后即可返回。交互式 shell 的终端控制初始化过程如下:

1. 交互式 shell 启动时必须先确认自己已经位于终端前台。如果它作为另一个 shell 的后台任务启动，直接操作终端会破坏外层 shell 的作业控制，所以应向自己的进程组发送 `SIGTTIN` 暂停，等待外层 shell 将它恢复到前台后再继续;
2. 随后 shell 确保自己是独立进程组的组长;
3. 忽略一般交互式控制信号; 这一步要在 `tcsetpgrp()` 前完成，以防在 setpgid 后创建了新进程组导致不再是前台进程组, 转而成为后台进程, 尝试设置前台进程组时会被内核挂起;
4. 把终端前台进程组设置为自己所在的 PGID;
5. 保存初始终端属性。

shell 自身同样需要集中保存状态。`pid` 和 `pgid` 区分 shell 进程与 shell 进程组，`terminal_modes` 保存 shell 使用终端时的属性，`jobs` 指向后台或暂停作业链表。原来散落的 `last_status` 和 `should_exit` 也一起收入 `ShellState`。

```c
// controller.h
typedef struct {
    pid_t pid;
    pid_t pgid;
    struct termios terminal_modes;

    Job *jobs;

    int interactive;
    int should_exit;
    int last_status;
} ShellState;

// controller.c
int controller_init(int interactive) {
    shell.pid = getpid();
    shell.pgid = getpgrp();
    shell.jobs = NULL;
    shell.last_status = 0;
    shell.should_exit = 0;
    shell.interactive = interactive;

    if (!shell.interactive)
        return 0;
    
    // 1. 检查自己是否在前台, 如果自己还不在前台进程组，就让内核用 SIGTTIN 暂停，等待父 shell 把我们切回前台后再继续。
    while (tcgetpgrp(STDIN_FILENO) != shell.pgid) {
        if (kill(-shell.pgid, SIGTTIN) == -1)
            return -1;
    }

    // 2. 确保 shell 是独立进程组的组长: pgid 等于 pid。
    if (shell.pgid != shell.pid) {
        if (setpgid(0, shell.pid) == -1)
            return -1;
        shell.pgid = getpgrp();
    }

    // 3. 忽略一般信号(在 tcsetpgrp 前, 防止 setpgid 后不再是前台进程组而被 SIGTTOU 挂起)
    if (shell_ignore_signals() == -1)
        return -1;

    // 4. 设置前台进程组为 shell 所在组
    if (tcsetpgrp(STDIN_FILENO, shell.pgid) == -1)
        return -1;

    // 5. 保存终端属性
    if (tcgetattr(STDIN_FILENO, &shell.terminal_modes) == -1)
        return -1;

    return 0;
}
```

终端生成的 `SIGINT`、`SIGQUIT` 和 `SIGTSTP` 应当作用于**当前前台 Job**，而不应杀死或暂停 shell。后台进程组读取控制终端时会收到 `SIGTTIN`；执行某些终端控制操作时会收到 `SIGTTOU`，启用 `TOSTOP` 后普通后台输出也会触发 `SIGTTOU`。shell 为了完成终端所有权切换，需要忽略这两个信号。

子进程会继承 shell 的信号处置。特别是被设置为忽略的信号在 `exec()` 后仍然保持忽略，因此每个子进程都必须在执行 builtin 或 `execvp()` 前恢复默认处置，否则用户按下 `Ctrl-C` 或 `Ctrl-Z` 时，前台任务也会无动于衷。

```c
int shell_ignore_signals(void) {
    if (signal(SIGINT,  SIG_IGN) == SIG_ERR) return -1;
    if (signal(SIGQUIT, SIG_IGN) == SIG_ERR) return -1;
    if (signal(SIGTSTP, SIG_IGN) == SIG_ERR) return -1;
    if (signal(SIGTTIN, SIG_IGN) == SIG_ERR) return -1;
    if (signal(SIGTTOU, SIG_IGN) == SIG_ERR) return -1;
    return 0;
}

int child_restore_signals(void) {
    if (signal(SIGINT,  SIG_DFL) == SIG_ERR) return -1;
    if (signal(SIGQUIT, SIG_DFL) == SIG_ERR) return -1;
    if (signal(SIGTSTP, SIG_DFL) == SIG_ERR) return -1;
    if (signal(SIGTTIN, SIG_DFL) == SIG_ERR) return -1;
    if (signal(SIGTTOU, SIG_DFL) == SIG_ERR) return -1;
    return 0;
}
```

- `getpid(void)`: 返回调用进程的 PID
- `getpgid(pid_t pid)`: 返回指定进程所在的进程组, 如果进程不存在，返回 -1; 如果传入的 pid 为 0, 则返回当前进程组ID(等同于`getpgrp(void)`)。
- `getsid(pid_t pid)`: 返回指定进程的会话 ID, 如果进程不存在，返回 -1; 如果传入的 pid 为 0, 则返回当前会话 ID。

- `tcgetpgrp(fd)` 返回终端当前的前台进程组。
- `tcsetpgrp(fd, pgid)` 将该终端的前台所有权交给指定进程组, 这里的 `fd` 必须引用当前会话的控制终端。原则上, 当前控制终端对应的 session 下的所有进程都可以尝试调用 `tcsetpgrp()` 去设置当前终端的**前台进程组**。但对于后台进程来说, 内核会向其发送 `SIGTTOU` 信号去挂起它, 避免**误抢占**(而不是避免**恶意抢占**), 而主 shell 正是由于忽略了 `SIGTTOU`, 才可以在处于后台的情况下回收前台进程的终端。

- `signal(signum, disposition)` 可以把信号处置设为默认动作 `SIG_DFL` 、忽略 `SIG_IGN` 或自定义信号处理函数。本项目只需要设置简单处置；如果以后安装真正的信号处理函数，应优先使用语义更明确、控制能力更完整的 `sigaction()`。

- `struct termios` 描述终端的输入、输出和控制模式，声明于 `<termios.h>` 中。

### 5.4 创建任务

executor 现在为所有需要 fork 的命令创建 Job，包括外部单命令、管道、后台 builtin 和普通后台命令。因为即使一个 Job 最初在前台运行，它也可能被 `Ctrl-Z` 暂停并转入作业表，所以**所有的前台子进程**同样需要 Job 结构。

#### 5.4.1 创建子进程进程组

同一条管道中的所有子进程必须进入同一个进程组，通常使用第一个子进程的 PID 作为 PGID。第一个子进程调用 `setpgid(0, self_pid)` 时创建以自己为组长的新进程组，后续子进程调用 `setpgid(0, first_pid)` 加入该组。

只让子进程调用 `setpgid()` 并不可靠：子进程与父进程在 `fork()` 后并发运行，只让子进程设置会使父进程在安排终端或继续 fork 时无法确定设置已经完成。而如果只让父进程调用, 父进程没有权限在子进程已经成功执行 `exec()` 后再替它修改进程组(会以 `EACCES` 失败)。因此需要父子两侧都调用 `setpgid()`，目标保持一致，由任意一侧先成功都可以消除这段竞态。

```c
// executer.c（fork 循环中的进程组核心逻辑）
pid_t pid = fork();
if (pid == -1)
    goto failed;

if (pid == 0) {
    if (child_restore_signals() == -1)
        _exit(1);

    /*
     * 第一个进程看到 job->pgid == 0，等价于 setpgid(0, 0)；
     * 后续进程看到第一个进程的 PID，加入同一进程组。
     */
    if (setpgid(0, job->pgid) == -1)
        _exit(1);

    handle_pipes(last_fds, current_fds, NULL, NULL);
    if (handle_redirs(command->redirs, NULL, NULL) == -1)
        _exit(1);

    /* 等待前台终端交接完成。 */

    char *fn_name =
        command->argv == NULL ? NULL : command->argv[0];
    builtin_fn fn = lookup_builtin(fn_name);
    if (fn != NULL) {
        int result = fn(command->argv);
        fflush(stdout);
        _exit(result);
    }

    execvp(fn_name, command->argv);
    _exit(127);
}

if (add_process(job, pid) == -1) {
    kill_wait_pid(pid);
    goto failed;
}

if (setpgid(pid, job->pgid) == -1 &&
    errno != EACCES && errno != ESRCH) {
    kill_wait_pid(pid);
    goto failed;
}
```

- `EACCES` 表示目标子进程已经越过 `exec()` 边界，父进程失去了替它修改进程组的权限；在父子双侧都调用 `setpgid()` 的设计中，通常意味着子进程已经完成设置。`ESRCH` 表示目标进程已经不存在。其他错误仍然必须报告和清理，不能因为“双重保险”就忽略所有返回值。

#### 5.4.2 使用管道门阻塞子进程

父进程只有在创建完 Job 的**全部进程**并把终端交给前台 Job 后才能运行子进程。否则先运行的子进程可能在终端仍属于 shell 时尝试读取输入，并被终端驱动以 `SIGTTIN` 暂停。

为此，交互式前台 Job 在 fork 前额外创建一个 `launch_gate` 管道。子进程完成进程组、管道和重定向设置后阻塞读取 gate；父进程 fork 完所有成员并调用 `tcsetpgrp()` 后关闭 gate 的写端，所有子进程读到 EOF，才开始执行真正的命令。后台 Job 不接管终端，也不需要这道启动门。

```c
int launch_gate[2] = {-1, -1};
/* 管道门, 只创建一次 */
if (shell.interactive && !commands->background) {
    if (pipe(launch_gate) == -1)
        goto failed;
}

/* 子进程完成 setpgid、管道和重定向之后读取阻塞 */
if (shell.interactive && !commands->background) {
    close(launch_gate[1]);

    char byte;
    while (read(launch_gate[0], &byte, 1) == -1) {
        if (errno == EINTR) continue;
        _exit(1);
    }

    close(launch_gate[0]);
}

if (commands->background) {
    // 后台任务无需管道门
} else {
    /* 父进程在全部 fork 完成、终端交接之后才能写入取消阻塞 */
    if (give_terminal(job) == -1)
        goto failed;

    close(launch_gate[0]);
    close(launch_gate[1]);

    int result = wait_foreground_job(job);

    if (take_terminal(job) == -1)
        goto failed;
}
```

#### 5.4.3 将终端交接给前台任务

终端交接不仅包括前台进程组，还包括终端属性。Job 获得终端时恢复自己保存的模式；shell 收回终端时先保存 Job 留下的模式，再恢复 shell 原本的模式。这样使用 `stty` 或全屏程序改变过终端配置的 Job 被暂停并 `fg` 后，仍然可以回到自己的终端环境。

```c
int give_terminal(Job *job) {
    if (!shell.interactive) return 0;

    while (tcsetpgrp(STDIN_FILENO, job->pgid) == -1) {
        if (errno == EINTR) continue;
        return -1;
    }

    return tcsetattr(STDIN_FILENO, TCSADRAIN,
                     &job->terminal_models);
}

int take_terminal(Job *job) {
    if (!shell.interactive) return 0;

    while (tcsetpgrp(STDIN_FILENO, shell.pgid) == -1) {
        if (errno == EINTR) continue;
        return -1;
    }

    if (tcgetattr(STDIN_FILENO,
                  &job->terminal_models) == -1)
        return -1;

    return tcsetattr(STDIN_FILENO, TCSADRAIN,
                     &shell.terminal_modes);
}
```

- `tcsetattr()` 修改终端属性，`TCSADRAIN` 表示等待已经排队的输出传输完成后再应用新设置，避免在输出途中突然改变终端模式。
- gate 管道在这里不传递实际数据，只利用“所有写端关闭后，读端返回 EOF”的性质充当一次性屏障。子进程不能永久保留任何写端，否则所有读取者都会一直等待。

#### 5.4.4 等待前台任务结束或放入后台

前台等待使用负 PGID，只回收当前 Job 中的子进程；`WUNTRACED` 使 `waitpid()` 在子进程被暂停时也返回。循环一直进行到 Job 的整体状态成为 DONE 或 STOPPED，而不是任意一个进程发生状态变化就结束。

shell 采用管道最后一条命令的状态作为整条管道的退出状态，所以等待结束后通过 `last_pid` 找到对应 Process，再从它保存的 `wait_status` 中提取退出码或信号编号。

```c
int wait_foreground_job(Job *job) {
    while (job->status != DONE &&
           job->status != STOPPED) {
        int status;
        pid_t pid = waitpid(-job->pgid, &status, WUNTRACED);

        if (pid == -1) {
            if (errno == EINTR) continue;
            if (errno == ECHILD) break;
            return 255;
        }

        update_process(job, pid, status);
    }

    Process *last = job->processes;
    while (last != NULL && last->pid != job->last_pid)
        last = last->next;

    if (last == NULL)
        return 255;
    if (WIFEXITED(last->wait_status))
        return WEXITSTATUS(last->wait_status);
    if (WIFSIGNALED(last->wait_status))
        return 128 + WTERMSIG(last->wait_status);
    if (WIFSTOPPED(last->wait_status))
        return 128 + WSTOPSIG(last->wait_status);
    return 0;
}
```

#### 5.4.5 维护后台作业表

后台 Job 启动后不能阻塞 REPL 等待，直接放入后台作业表中:

```c
if (commands->background) {
    // 后台任务直接加入后台作业表
    if (job_add(job) == -1) {
        perror("job_add");
        goto failed;
    }
    ret_code = 0;
} else {
    // 前台任务终端交接、取消阻塞、等待任务结束
}

但退出后的子进程仍然必须由 shell 回收。`check_jobs()` 在每轮打印提示符前以及执行作业控制 builtin 前调用 `waitpid()`，使用 `WNOHANG` 排空当前所有可处理的状态变化。

这里不在 `SIGCHLD` 信号处理函数中直接修改链表。链表分配、释放和 stdio 输出都不适合放进异步信号处理函数；在 REPL 的安全位置主动轮询，虽然完成通知可能要到下一轮提示符才出现，但实现更简单且不会破坏内存结构。

```c
void check_jobs(void) {
    while (1) {
        int status;
        pid_t pid = waitpid(-1, &status,
                            WNOHANG | WUNTRACED | WCONTINUED);

        if (pid == 0)
            break;
        if (pid == -1) {
            if (errno == EINTR) continue;
            if (errno == ECHILD) break;
            perror("check_jobs");
            break;
        }

        /*
         * 在 shell.jobs 中找到 pid 所属的 Job，
         * 更新 Process，再根据 Job 的新旧状态输出
         * Done、Stopped 或 Continued；DONE 后移出并释放。
         */
        update_process(NULL, pid, status);
    }
}
```

作业链表的顺序同时承担 current job 和 previous job 的语义：链表头是 `%+`，第二个节点是 `%-`。某个 Job 新增、停止或被 `bg` 操作时，将它移动到链表头。这样 Job 结束并被删除后，后续节点会自然前移，不需要维护可能悬空的 `current`、`previous` 指针。

```c
void job_make_current(Job *job) {
    if (job == NULL || shell.jobs == job)
        return;

    Job **link = &shell.jobs;
    while (*link != NULL) {
        if (*link == job) {
            *link = job->next;
            break;
        }
        link = &(*link)->next;
    }

    job->next = shell.jobs;
    shell.jobs = job;
}
```

Job ID 与链表位置是两个独立概念。链表按“最近成为 current”的顺序排列，ID 则使用当前最小的空缺正整数，并允许在旧 Job 结束后复用。若当前共有 `n` 个 Job，那么 `1` 到 `n + 1` 中必然至少有一个可用 ID；因此只需分配一个 `n + 2` 大小的 used 数组，扫描两遍链表即可在线性时间内找到空缺。

```c
static int allocate_job_id(size_t *result) {
    size_t count = 0;
    for (Job *job = shell.jobs;
         job != NULL;
         job = job->next) {
        if (count == SIZE_MAX - 1) {
            errno = EOVERFLOW;
            return -1;
        }
        count++;
    }

    unsigned char *used = calloc(count + 2, sizeof(*used));
    if (used == NULL) return -1;

    for (Job *job = shell.jobs;
         job != NULL;
         job = job->next) {
        if (job->job_id > 0 && job->job_id <= count + 1)
            used[job->job_id] = 1;
    }

    for (size_t id = 1; id <= count + 1; id++) {
        if (!used[id]) {
            *result = id;
            free(used);
            return 0;
        }
    }

    free(used);
    errno = EOVERFLOW;
    return -1;
}
```

- 使用 `Job **link` 指向“保存当前节点指针的位置”，可以统一处理删除链表头和删除中间节点，不需要为头节点单独编写分支。
- job ID 是 shell 为用户显示和查找作业分配的编号，不是 PID 或 PGID。复用已释放的空缺可以避免长时间运行的 shell 让编号无界增长。
- 上述编号算法的时间复杂度和额外空间复杂度均为 `O(n)`。相比小根堆，它更适合规模通常很小的交互式作业表，也更容易保证链表顺序与编号分配相互独立。

### 5.5 实现 `jobs`、`fg` 与 `bg` 内置命令

作业控制命令使用 jobspec 引用作业，使用 `% + JobID` 的形式与直接使用 `PID` 的 `kill` 等命令相区别。`%n` 表示 job ID 为 `n` 的作业，`%`、`%%` 和 `%+` 表示 current job，`%-` 表示 previous job；省略参数时同样选择 current job。前导 `%` 明确告诉 shell 这里引用的是作业表编号，避免与进程 PID 或普通数字参数混淆。

```c
static Job *resolve_jobspec(const char *jobspec) {
    if (jobspec == NULL ||
        strcmp(jobspec, "%") == 0 ||
        strcmp(jobspec, "%%") == 0 ||
        strcmp(jobspec, "%+") == 0) {
        return shell.jobs;
    }

    if (strcmp(jobspec, "%-") == 0)
        return shell.jobs == NULL ? NULL : shell.jobs->next;

    if (jobspec[0] != '%' || jobspec[1] == '\0')
        return NULL;

    errno = 0;
    char *endptr;
    unsigned long long id =
        strtoull(jobspec + 1, &endptr, 10);

    if (errno == ERANGE || *endptr != '\0' ||
        id == 0 || id > SIZE_MAX)
        return NULL;

    for (Job *job = shell.jobs;
         job != NULL;
         job = job->next) {
        if (job->job_id == (size_t)id)
            return job;
    }
    return NULL;
}
```

`jobs` 先调用 `check_jobs()` 取得最新状态，再按链表顺序打印所有作业。链表头使用 `+` 标记，第二个节点使用 `-` 标记，其余作业不带特殊标记。

```c
static int builtin_jobs(char **argv) {
    (void)argv;
    check_jobs();

    for (Job *job = shell.jobs;
         job != NULL;
         job = job->next) {
        char marker = job == shell.jobs ? '+' :
                      (job == shell.jobs->next ? '-' : ' ');
        const char *status =
            job->status == RUNNING ? "Running" :
            job->status == STOPPED ? "Stopped" : "Done";

        printf("[%zu]%c %-7s %s\n",
               job->job_id, marker, status, job->cmd);
    }
    return 0;
}
```

`bg` 不接管终端，只向整个进程组发送 `SIGCONT`，把暂停的 Process 标记为 RUNNING，并将该 Job 移到 current 位置。它可以依次处理多个 jobspec。

```c
static int continue_in_background(Job *job) {
    if (kill(-job->pgid, SIGCONT) == -1)
        return 1;

    job_mark_running(job);
    job->background = 1;
    job_make_current(job);

    printf("[%zu]+ Running %s\n",
           job->job_id, job->cmd);
    return 0;
}
```

`fg` 的顺序更严格：先把 Job 暂时移出后台链表并标记为前台，再把终端交给该进程组；如果 Job 原本处于 STOPPED，则发送 `SIGCONT` 并更新状态；随后阻塞等待，最后由 shell 收回终端。Job 如果正常结束就释放，如果再次被暂停则重新加入作业表。

```c
static int builtin_fg(char **argv) {
    check_jobs();
    Job *job = resolve_jobspec(argv[1]);
    if (job == NULL) return 1;

    int was_stopped = job->status == STOPPED;
    Job **link = &shell.jobs;
    while (*link != NULL) {
        if (*link == job) {
            *link = job->next;
            job->next = NULL;
            break;
        }
        link = &(*link)->next;
    }
    job->background = 0;

    if (give_terminal(job) == -1) {
        job->background = 1;
        job_make_current(job);
        return 1;
    }

    if (was_stopped) {
        if (kill(-job->pgid, SIGCONT) == -1) {
            take_terminal(job);
            job->background = 1;
            job_make_current(job);
            return 1;
        }
        job_mark_running(job);
    }

    int result = wait_foreground_job(job);
    if (take_terminal(job) == -1)
        result = 1;

    if (job->status == STOPPED ||
        job->status == RUNNING) {
        job->background = 1;
        if (job_add(job) == -1) {
            kill_wait_job(job);
            free_job(job);
            return 1;
        }
    } else {
        free_job(job);
    }

    return result;
}
```

`SIGCONT` 只负责让内核恢复进程，不会自动修改用户空间中的 Job/Process 数据，所以发送成功后仍需调用 `job_mark_running()`。相反，后台进程之后真正发生的退出、停止和继续事件仍以 `waitpid()` 返回结果为准。

`fg` 和 `bg` 依赖交互式终端与当前 shell 的作业表，因此在 `-c` 或脚本模式下应报告 job control 不可用。它们对进程组发送信号，而不是逐个遍历 PID；这样即使 Job 是多段管道，所有成员也会作为一个整体继续、停止或获得终端。

### 5.6 作业控制的问题

不论是 bash、zsh 还是我们的 mysh, 作业控制都是一种**与子进程的约定**, 其并没有办法强制子进程遵守这个约定。

以创建进程组为例, 我们会讲管道内的所有子进程组成一个进程组, 后续都将以该 PGID 为标记来进行回收、发送信号和终端交接等操作。然而, 如果子进程想要**恶意**脱离管辖, 它可以在 `exec` 后继续调用 `setpgid(0, 0)` 创建一个新的进程组(如果它不是管道的第一个进程的话), 这样它就不再属于父 shell 的进程组了。此时, 父 shell 对该子进程的信号发送和回收操作都将失效。比如现在有一个恶意进程 evil:

```c
// evil.c
#include <unistd.h>

int main() {
    setpgid(0, 0);
    while (1);
}
```

然后父 shell 以如下方式启动它:

```bash
> echo "start evil" | ./evil | echo "end evil"
```

此时父 shell 将被完全卡死, 即使使用 Ctrl+C 中断、 Ctrl+Z 挂起都无法返回, 因为子进程已经脱离了原有进程组成为了一个**新的后台进程组**, 前台终端信号将不再传递给它。

又比如, 如果有后台进程**恶意**忽略 `SIGTTIN` 和 `SIGTTOU` 信号, 那么它就可以在后台不断调用 `tcsetpgrp()` 抢占终端, 让前台进程无法正常读取输入, 并且在后台不断输出干扰终端显示。bash 和 zsh 都没有办法阻止这种行为, 只能依赖子进程遵守约定。

```c
// evil.c
#include <unistd.h>
#include <signal.h>
#include <termios.h>

int main() {
    signal(SIGTTIN, SIG_IGN);
    signal(SIGTTOU, SIG_IGN);

    while (1) {
        tcsetpgrp(STDIN_FILENO, getpgrp());
        write(STDOUT_FILENO, "evil\n", 5);
        sleep(1);
    }
}
```

## 总结

完成本阶段后，mysh 已经不再只是“执行一条命令并等待”的同步启动器，而是能够持续管理一组具有生命周期的作业：

- `tokenizer.h/.c` 与 `parser.h/.c`：识别末尾的 `&` 并记录后台执行属性；
- `controller.h/.c`：保存 shell 全局状态，初始化交互式进程组，管理信号与终端所有权；
- `job.h/.c`：维护 Job、Process、等待状态、作业链表和 job ID；
- `executer.c`：为每次 fork 执行建立进程组，区分前后台等待并处理暂停作业；
- `builtin.c`：通过 `jobs`、`fg` 和 `bg` 操作作业表及对应进程组；
- `shell.c`：在 REPL 的安全位置检查后台状态变化。

至此，mysh 的基础 shell 大框架已经完成：它能够解析并展开命令，执行 builtin 与外部程序，建立重定向和任意长度管道，并在交互式终端中管理前台、后台、停止与继续的作业。未实现的 IFS 分词、通配符、命令替换和复合语法属于后续功能扩展，不再影响当前核心执行模型的完整性。
