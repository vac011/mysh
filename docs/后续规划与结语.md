# 6. 后续规划与结语

## 当前完成度

到第五阶段为止，mysh 已经建立了一个基础交互式 shell 最重要的主体结构：

- 从交互终端、`-c` 参数或脚本文件中读取命令；
- 将文本依次转换为 Token、展开后的 WORD 和 Command 管道结构；
- 区分并执行 builtin 与外部程序；
- 使用文件描述符实现重定向和任意长度管道；
- 使用进程组、终端前台所有权和信号实现作业控制；
- 支持后台执行以及 `jobs`、`fg`、`bg`。

这意味着当前项目已经不是一个只能调用 `execvp()` 的命令启动器。输入解析、进程创建、文件描述符编排、状态回收和终端控制已经形成闭环，继续增加功能不会推翻现有核心模型。

与此同时，mysh 仍然只是 Bash/zsh 的一个核心子集。它没有完整的 shell 展开顺序、控制运算符、脚本语言和交互编辑能力。这些缺失并不否定当前版本的完整性，只是说明后续工作已经从“补齐基础 shell 框架”转变为“选择希望深入的方向”。

## 建议安排

如果继续开发，不建议按照看到一个 Bash 特性就增加一个分支的方式前进。后续功能之间已经出现明显的依赖关系：IFS 和 glob 需要保留引号信息，`&&` 和 `||` 需要新的语法树，变量赋值和控制语句又建立在它们之上。比较稳妥的顺序如下：

| 阶段 | 主要内容 | 完成后的结果 |
| --- | --- | --- |
| 0 | 固化当前版本 | 得到一个可以随时回到的 mysh v1 |
| 1 | 测试与可靠性收尾 | 当前功能具有稳定的回归基线 |
| 2 | 完善文件描述符与重定向 | 能表达常见的标准错误和 fd 复制操作 |
| 3 | 重构 WORD 与展开模型 | 正确实现 IFS、glob 和更丰富的参数展开 |
| 4 | 引入 AST 与控制运算符 | 支持多条命令、条件执行和子 shell |
| 5 | 按兴趣选择脚本语言或交互体验 | 从基础 shell 进入解释器或终端产品方向 |

这些阶段不需要全部完成。做到阶段 1 后停止，当前项目已经可以作为一个完整的系统编程作品；做到阶段 3，能够进一步理解 shell 最复杂的文本语义；继续进入阶段 4、5，则项目重心会逐渐从进程管理转向语言解释器。

### 6.1 固化当前版本

首先应当为现在的代码建立一个明确版本，例如创建 `v1.0` tag，并在 README 中写清楚已经支持和暂不支持的行为。这样后续重构 expander 或 parser 时，即使中间版本暂时不可用，也始终保留一个完成了核心框架的基线。

README 不需要重复开发手册，只需要让第一次看到项目的人快速知道：

- mysh 的编译和启动方式；
- 当前支持的命令形式；
- 引号、变量、管道、重定向和作业控制示例；
- 与 Bash/zsh 有意不同的行为；
- 尚未实现的语法边界。

还可以录制一段很短的终端演示，依次展示管道、重定向、后台执行、`Ctrl-Z`、`bg`、`fg` 和 `Ctrl-C`。对于 shell 项目而言，这比单独罗列源文件更能直观说明它已经具备哪些能力。

### 6.2 测试与可靠性收尾

在增加新语法前，最值得做的不是继续扩充代码，而是把当前已经实现的行为固定下来。否则未来对 tokenizer、parser 或 executor 的任何修改，都可能悄悄破坏作业控制或文件描述符关闭时序。

测试可以分为两类：

- **非交互测试**：通过 `./mysh -c` 或脚本文件测试 argv、引号、变量展开、重定向、管道和退出状态。这类测试可以比较标准输出、标准错误、返回值和生成文件内容。
- **PTY 测试**：在伪终端中启动 mysh，向它发送 `Ctrl-C`、`Ctrl-Z`，再执行 `jobs`、`bg` 和 `fg`。普通管道无法模拟控制终端及前台进程组，因此作业控制不能只依赖非交互测试。

建议至少保存以下回归案例：

- 空行、空引号、未闭合引号和孤立反斜杠；
- builtin、外部命令和不存在的命令；
- 多个连续重定向及重定向失败；
- 两段和多段管道、管道与重定向组合；
- 无命令重定向；
- 前台命令被 `Ctrl-C` 终止；
- 前台管道被 `Ctrl-Z` 暂停，再经过 `bg`、`fg` 恢复；
- 多个后台 Job 的 current/previous 顺序和 job ID 复用。

编译阶段可以继续使用 AddressSanitizer，并增加 UndefinedBehaviorSanitizer。macOS 与 Linux 都应至少运行一次完整测试，因为终端、`signal()` 和部分扩展接口的细节可能不同。测试的重点不是证明 mysh 与某个 shell 的所有输出完全一致，而是保证已经明确选择的 mysh 语义不会意外改变。

这一阶段还应补齐错误与退出路径：

- 检查关键 `dup()`、`dup2()`、`pipe()`、`tcsetpgrp()` 和内存分配调用的返回值；
- 确保部分 fork 成功、随后执行失败时，已经创建的进程和文件描述符都能回收；
- 明确 shell 退出时如何处理仍在运行或暂停的 Job；
- 使用 `sigaction()` 逐步替代 `signal()`，明确控制信号屏蔽字和 `SA_RESTART`，减少不同平台历史语义带来的差异；
- 将模块的借用指针、所有权转移和销毁顺序写在对应头文件中；
- 逐步减少聚合式 `shell.h` 带来的无关模块依赖。

shell 退出时的 Job 策略需要有意识地选择。可以先采用简单方案：发现仍有 Job 时给出提示并拒绝第一次退出；再次退出时向作业进程组发送 `SIGHUP`/`SIGCONT` 并完成回收。以后再增加 `disown`，允许用户明确把某个 Job 从作业表中移除。

后台状态检查目前放在 REPL 的安全位置主动执行，这是一个合理的基础实现。暂时没有必要为了“看起来更异步”就在 `SIGCHLD` handler 中直接分配内存、释放链表或打印信息。如果未来确实需要立即通知，可以让 handler 只写入 self-pipe，再由主循环在普通执行环境中处理作业状态。

### 6.3 完善重定向模型

当前 `Redirector` 只区分 `<`、`>` 和 `>>`，默认操作标准输入或标准输出。下一步可以把它扩展为真正的文件描述符操作：

- `2> error.log`、`2>> error.log`；
- `2>&1`、`1>&2`；
- `n<&m`、`n>&m`；
- `n>&-` 关闭文件描述符；
- `<>` 以读写方式打开文件；
- here-document `<<` 和 here-string `<<<`。

这时 `Redirector` 不应继续只保存 TokenType 和文件名，而应至少表达：

- 源文件描述符，例如 `2>` 中的 `2`；
- 操作类型，例如打开文件、复制 fd 或关闭 fd；
- 目标是路径、另一个 fd，还是 here-document 内容。

所有重定向仍然必须严格按照出现顺序执行：

```sh
command > output 2>&1
command 2>&1 > output
```

第一条先让 stdout 指向文件，再让 stderr 复制当前 stdout，因此两者都进入文件；第二条先让 stderr 复制原来的 stdout，再单独修改 stdout，因此 stderr 仍然输出到终端。不要把重定向预先合并成“最终 stdin/stdout/stderr”，否则会丢失这种顺序语义。

tokenizer 还需要保留数字与重定向符之间是否相邻的信息：`2>error.log` 中的 `2` 是源文件描述符，而 `2 >error.log` 中的 `2` 是普通 argv。可以增加只在数字紧邻重定向符时产生的 `IO_NUMBER` Token，不能在 parser 中仅凭前一个 WORD 的内容猜测。

here-document 可以最后实现，因为它不仅是一次 `open()`：parser 需要保存 delimiter，主循环需要继续读取多行输入，delimiter 是否被引号包围还决定正文要不要进行参数展开。它同时跨越 tokenizer、parser、expander 和 REPL，不适合与普通重定向一起仓促加入。

### 6.4 重构 WORD 与展开模型

如果准备实现 IFS、通配符或完整参数展开，当前“Token 中只保存一个原始字符串，expander 最后得到一个新字符串”的表示就接近极限了。

原因在于展开后的字符是否允许分词和 glob，取决于它原来是否被引号保护：

```sh
value="a b"
printf '<%s>\n' $value
printf '<%s>\n' "$value"
```

两次 `$value` 得到的文本相同，但前者允许 IFS 分词，后者必须保留为一个参数。如果 expander 过早删除引号并只留下 `"a b"`，后续阶段已经无法恢复这段文本原来的引号环境。

因此，在继续扩展前建议把 WORD 改为若干带属性的片段，例如：

```text
Word
├── NORMAL: "prefix"
├── DOUBLE: "$HOME"
└── SINGLE: "*"
```

也可以为每个输出字符保存 quoted 标记。具体结构不重要，关键是不变量：**在 field splitting 和 pathname expansion 完成前，不能丢失字符是否受到引号保护的信息。**

在新的表示上，可以按以下顺序逐步增加能力：

1. 波浪号展开 `~`；
2. 更完整的参数展开 `${VAR}`、`${VAR:-default}`、`${#VAR}`；
3. 命令替换 `$(command)` 与算术展开 `$((expression))`；
4. 只对未引用结果进行 IFS field splitting；
5. 只对未引用的 `*`、`?`、`[...]` 进行 pathname expansion；
6. 最后完成 quote removal，生成真正的 argv。

不建议在环境变量展开后直接调用 `strtok()` 实现 IFS，也不建议对最终字符串无条件调用 `glob()`。这两种做法都会错误拆分双引号中的空格，或展开本应被引号保护的通配符。

命令替换本身可以复用现有执行器：创建管道，在子进程中执行一段命令，将其标准输出读回并删除所有结尾换行。但它还要求 parser 能够识别成对的 `$(` 与 `)`，并处理内部嵌套，因此最好放在新的 WORD/AST 模型建立之后。

### 6.5 从 Commands 链表升级为 AST

当前 `Commands` 很适合表达一条管道，但无法自然表示：

```sh
make && echo success || echo failed
cd /tmp; pwd
(cd /; pwd) | cat
```

如果要支持 `;`、`&&`、`||`、`!`、`(...)` 和 `{...;}`，继续在 `Commands` 中增加 `has_and`、`has_or`、`subshell` 等布尔字段会很快产生无法维护的组合状态。此时 parser 应从“构造 Command 链表”升级为“根据运算符优先级构造 AST”。

一个足够起步的节点集合可以包括：

- SimpleCommand：argv 与重定向；
- Pipeline：若干 SimpleCommand；
- AndOr：`&&` 或 `||` 连接的左右节点；
- List：由 `;` 或 `&` 连接的多个节点；
- Subshell：在独立子进程中执行的子树。

解析优先级应从高到低逐层建立：

```text
simple command / redirection
        ↓
pipeline（|，以及前缀 !）
        ↓
and-or（&&、||）
        ↓
list（;、&、换行）
```

executor 随后递归执行 AST：`&&` 只在左侧成功时执行右侧，`||` 只在左侧失败时执行右侧，`;` 无条件继续，subshell 则 fork 后执行整棵子树。现有的管道和 Job 启动代码仍然可以作为 Pipeline 节点的执行后端，不需要重写。

完成 AST 后，当前“`&` 必须位于整行末尾”的限制也可以自然解除，因为 `&` 将成为 list 层的连接符，而不再只是 Commands 上的一个布尔标志。

### 6.6 脚本语言与交互体验

AST 建立后，如果希望把 mysh 继续发展成脚本解释器，可以依次实现：

- shell 变量、环境变量以及 `export`、`unset`；
- 命令前变量赋值 `NAME=value command`；
- 脚本参数 `$0`、`$1`、`$@`、`$#`；
- `if`、`while`、`for`、`case`；
- shell function、`return`、局部变量；
- `break`、`continue` 和更完整的 `exit` 语义。

这些功能的难点不再主要是系统调用，而是作用域、执行环境和控制流。例如独立 builtin、subshell、管道成员和命令替换对变量的修改是否能够返回父 shell，需要由统一的执行环境模型决定，不能只根据命令名临时判断。

如果更关心交互式终端体验，而不是脚本语言，则可以选择另一条路线：

- 使用 GNU Readline 或 libedit 实现行编辑；
- 保存与搜索历史命令；
- 补全命令、路径、变量和 jobspec；
- 支持可配置提示符；
- 增加 `wait`、`kill`、`disown` 等作业 builtin；
- 完善 `%name`、`%?substring` 等 jobspec。

行编辑库会接管终端输入模式，与现有 job control 共享同一个控制终端。接入时应重新验证前台程序退出、暂停或修改 termios 后，mysh 是否能够恢复编辑器需要的终端状态。

## 如何选择下一步

后续路线应该由学习目标决定，而不是由 Bash 的功能数量决定。

如果目标仍然是**系统编程训练**，我建议完成版本固化、自动测试、错误路径和 fd 重定向后就暂时停止。当前项目已经覆盖进程、文件描述符、信号、终端和并发时序，再继续实现 `if`、`for` 和函数，新增知识会越来越偏向解释器设计。此时转向网络服务器、事件循环、调试器或容器运行时，会比继续追逐 Bash 的边角行为获得更多新的系统经验。

如果目标是继续学习**编译原理和解释器**，则应优先重构 WORD 表示和 parser，建立带引号属性的展开模型与 AST。这个方向下，IFS、glob、命令替换和控制语句不是几个孤立特性，而是一门小型语言从词法、语法到执行环境的完整实现。

如果目标是做成一个自己长期使用的**交互工具**，则应优先接入 Readline/libedit、历史和补全，并把跨平台终端行为、崩溃恢复和配置能力放在语法兼容之前。

三个方向都合理，但不建议同时推进。选定一个方向做出完整闭环，比每个方向各实现一半更有价值。

## 结语

这个项目最有价值的部分，不是最终支持了多少条命令，而是它迫使许多原本模糊的概念变得具体：

- 一行字符串如何逐步变成 Token、Command、Process 和 Job；
- 一个指针究竟拥有内存，还是只借用另一个对象的生命周期；
- 一个文件描述符为什么必须在正确的进程、正确的时间关闭；
- `fork()` 后的两个进程为什么不会共享普通内存修改；
- 管道为什么不是“把两个命令连起来”这么简单，而是一组需要严格管理的 fd 引用；
- Job 为什么不是 PID 列表，而是进程组、终端所有权和状态机共同形成的抽象；
- shell 行为为什么不能只凭印象推断，而需要查阅规则并在真实 Bash、zsh 和终端中验证。

从最初只能回显输入的 REPL，到现在能够启动多段管道、接收 `Ctrl-Z`、在后台继续并重新 `fg` 的交互式 shell，mysh 已经完成了它作为学习项目最重要的任务：把 Unix 进程模型从书本上的名词变成了可以亲手观察、修改和调试的运行系统。

我最想留下的建议是：保留现在这份完成感，不要因为 Bash 还有大量未实现功能，就把当前成果称为“还没做完”。完整复刻 Bash 是另一个数量级的工程，而基础 shell 的核心框架已经完成。接下来无论选择继续扩展、重构为解释器，还是就此封存并开始下一个项目，都不是半途而废，而是在一个清晰的边界上主动选择下一段路。
