评判

1. feof(stdin) 的用法是错的,这是 C 初学者最经典的坑。

你这逻辑链是:getline 返回 -1 → 检查 errno == EINTR → 否则检查 feof(stdin) → 否则 perror。这个判断顺序看着合理,但 feof 在这里是个错误工具。

feof(f) 的语义是:"f 的 EOF 指示器是否被置位"。它只有在某次读取操作已经撞上 EOF 之后才为真——它告诉你的是"上次读操作的状态",不能用来预判"下一次读会不会成功"。正确的"读到 EOF"判断从来不是靠 feof,而是靠读取函数本身的返回值:getline 返回 -1 且 errno 不是 EINTR,那就是 EOF 或真错误——feof(stdin) 此时碰巧为真而已,你把它当判据是本末倒置。

更要命的是:getline 返回 -1 时,它不保证给你设置 errno。POSIX 原文:getline 在 EOF 时返回 -1,且不设置 errno(只在真正 I/O 错误时才设)。所以你的 errno == EINTR 判断在 getline 这里基本是空中楼阁——getline 不是 read,它内部循环处理了 EINTR。这段判断对 getline 几乎是永远走不到的死分支。

正确写法记牢这个模式:

nread = getline(...)
if (nread == -1) {
    if (feof(stdin)) { /* 干净的 EOF,退出 */ }
    else { perror("getline"); /* 真错误 */ }   // 真错误时 errno 才有意义
    break;
}

也就是说:EOF 用 feof 判(这是它唯一正确的用法——事后确认是不是干净 EOF),真错误才轮到 errno。顺序反过来了。你现在反着用,虽然"碰巧"能退出,但模型是错的。改对它。理解了再写,别照抄。

2. errno = 0; 手动清零——暴露了你对 errno 的根本误解。

你写 errno = 0 是因为你直觉觉得"我得先把遗留的 errno 抹掉,不然读不完"。这反映你心里把 errno 当成了一个"会被上一轮残留污染"的脏变量。errno 不是状态机,它只在库函数发生错误的那一瞬间被写入,不调用任何库函数它就不会自己变。 你 errno = 0 后立刻调 getline,中间没有别的库调用,清不清零无所谓;清零唯一的意义是 "反正都要检查了先归位" 这种防御式迷信。真正的纪律是:检查 errno 的前提是"刚刚调用的那个函数明确报告了失败",而不是"我提前把场子打扫干净了再说"。把 errno = 0 删掉,在 elif 链里只在"真失败"分支读 errno。如果按第 1 点改成 feof 在前,这行就自然消失了。

你第 3 步的 tokenizer 是黑名单状态机:is_word_char 决定一个字符走 word 还是元字符。但那个状态机只有一个状态(在/不在 word)。bash 引号要求一个多状态机:
